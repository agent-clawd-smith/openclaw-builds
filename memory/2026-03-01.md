## Session: iMessage Portal Visibility Investigation (12:41–12:57 PM)

### What we tried
1. **Removed imessage agent, routed through main agent** — caused session file lock conflict (`58b76e6f...jsonl.lock`) whenever webchat is active. Main agent can only serve one active session at a time.
2. **`--session-id <stable-uuid-per-person>`** — ignored by gateway; still routes through main lane, still locks.
3. **`--to <number> --session-id <uuid>`** — same result, lock conflict.
4. **`--agent main --session-id <uuid>`** — same, always hits the main session lock.

### Conclusion
**Hard OpenClaw limitation:** While the webchat session is active, no `openclaw agent` CLI call to the main agent can succeed — gateway routes all calls through the main lane which is locked by the active webchat. `--session-id` does NOT create a concurrent separate session in the main agent.

### Resolution
Reverted to `--agent imessage`. The imessage agent has its own session namespace, no lock conflicts, everything works. Downside: iMessage sessions not visible in main portal (portal only shows one agent's sessions at a time — an upstream OpenClaw limitation).

### Portal session structure (final state)
- `agent:main:main` = webchat (this session) ✅ visible in portal
- `agent:imessage:+19163030339` etc = iMessage sessions ✅ work perfectly, NOT visible in main portal
- `agent:imessage:main` = default imessage session (noise, not important)
